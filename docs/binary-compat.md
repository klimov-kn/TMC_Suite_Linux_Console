# ⚠️ Бинарная совместимость файлов Windows ↔ Linux

> **Это главный технический риск проекта.** Заказчик считает на Linux, а результаты
> смотрит на Windows в уже собранном TMC Suite (ответы #8, #16). Файлы — вход и
> выход — обязаны быть **байт-в-байт** совместимы. Без этого проект бессмысленен.

## Три источника несовместимости

### 1. Размер типа `long` — LLP64 против LP64 🔴

| | Windows x64 (MSVC) | Linux x86-64 (g++) |
|---|---|---|
| Модель данных | **LLP64** | **LP64** |
| `int` | 32 бита | 32 бита |
| `long` | **32 бита** | **64 бита** ← расходится! |
| `long long` | 64 бита | 64 бита |
| указатель | 64 бита | 64 бита |

**Следствие:** если в формате файла поле объявлено как `long`, на Windows оно
занимает 4 байта, на Linux — 8. Запись на Linux → смещение всех последующих полей →
Windows читает мусор.

**Решение:** в коде сериализации/десериализации использовать **фиксированные по
ширине типы** из `<cstdint>`:

| Было (Windows-код) | Должно стать |
|---|---|
| `long` (4 байта на Win) | `int32_t` |
| `unsigned long` | `uint32_t` |
| `int` | `int32_t` (на обеих платформах и так 4 байта, но фиксируем явно) |
| `__int64` (MSVC) | `int64_t` |

> Это **не изменение математики** — это фиксация ширины полей формата. Допустимая
> механическая правка. Записывать в [../ISSUES.md](../ISSUES.md).

### 2. Порядок байт (endianness) ✅ совпадает

И Windows x64, и Linux x86-64 — **little-endian**. Целевая архитектура одна (Intel,
ответ #4), поэтому порядок байт совпадает и проблемы НЕ создаёт. Но если когда-нибудь
зайдёт речь про ARM/Эльбрус (сейчас не актуально) — пересмотреть.

### 3. Кодировка текстовых полей — CP1251 🟡

Русские строки в файлах хранятся в **Windows-1251**. Linux работает в UTF-8.

**Правило:** текстовые поля внутри файлов трактуем как **сырые байты** и переносим
без перекодирования. Если перекодировать в UTF-8 — Windows-версия покажет
«кракозябры», совместимость сломается. Перекодировка допустима только при выводе в
консоль/лог для человека, но НЕ в файлы данных.

## Дополнительные тонкости

- **Выравнивание и `#pragma pack`.** Если структуры пишутся в файл целиком
  (`fwrite(&struct, ...)`), правила выравнивания MSVC и g++ должны совпадать.
  Проверить наличие `#pragma pack` и сохранить идентичную упаковку. Безопаснее —
  сериализовать поля поодиночке, а не структуру целиком.
- **`float` vs `double`.** В Windows-проекте закреплён `_PREC_DOUBLE` (Баг #11): поле
  пишется 8-байтовыми `double`. На Linux держать то же — иначе и формат разъедется, и
  X-схема станет нестабильной.
- **Перевод строк.** Текстовые файлы: Windows `\r\n` vs Linux `\n`. Если формат
  текстовый — открывать в бинарном режиме (`"rb"/"wb"`) и не давать рантайму
  подменять переводы строк.

## Критерий приёмки

Файл, посчитанный нашим Linux-бинарником на эталонном входе, при бинарном сравнении
(`cmp`/`fc`) с файлом от Windows-версии на том же входе должен **совпасть байт-в-байт**
(с поправкой только на заведомо переменные поля — дата/время, если они есть). Проверка
автоматизирована — см. [../tests/README.md](../tests/README.md) и скилл
`verify-binary-compat`.
